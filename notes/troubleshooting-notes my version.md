# Troubleshooting Notes 

## Issue 1 — PowerShell HTTP Hunt Returned No Results

### Original Query

```esql
FROM logs-*
| WHERE process.name IN ("powershell.exe", "pwsh.exe")
| WHERE process.command_line LIKE "*http*"
| KEEP @timestamp, host.name, user.name, process.name, process.pid, process.parent.name, process.command_line, process.executable
| SORT @timestamp DESC
```

### Result

```text
0 documents processed
```

### Investigation

The actual network request was generated by:

```text
curl.exe
```

not by PowerShell directly.

The process chain was:

```text
pwsh.exe
    |
    +-- curl.exe
```

The URL existed in the `curl.exe` command line, not necessarily in the parent PowerShell process command line.

### Resolution

Search for the actual network-generating process:

```esql
FROM logs-*
| WHERE process.name == "curl.exe"
| KEEP @timestamp, host.name, user.name, process.name, process.pid, process.parent.name, process.parent.pid, process.command_line, process.executable
| SORT @timestamp DESC
```

### Lesson

The process that launches a network utility is not necessarily the process that directly owns the network connection.

## Issue 2 — Network Events Were Broader Than the Controlled Activity

A TCP/443 query returned many events.

Observed processes included:

```text
chrome.exe
Photos.exe
curl.exe
```

### Investigation

The endpoint was already generating normal HTTPS traffic.

Therefore, a broad:

```text
destination.port == 443
```

query was useful for baseline analysis but insufficient for identifying the controlled event by itself.

### Lesson

Network investigation should combine:

```text
Destination
+
Process
+
User
+
Timestamp
```

rather than relying on the destination port alone.

## Issue 3 — Destination Address Needed to Be Derived From DNS

`example.com` resolved to multiple addresses.

Observed:

```text
172.66.147.243
104.20.23.154
```

and an IPv6 address.

The controlled Elastic network event referenced:

```text
172.66.147.243
```

### Resolution

The destination returned by Elastic was used directly for the focused network query:

```esql
FROM logs-*
| WHERE destination.address == "172.66.147.243"
| KEEP @timestamp, host.name, user.name, process.name, process.pid, process.parent.name, destination.address, destination.port, network.transport
| SORT @timestamp DESC
```

### Lesson

Do not assume a hostname maps to one permanent IP address.

Use the destination actually observed in the telemetry being investigated.

## Issue 4 — Network Event Did Not Show Every Process Field

The controlled network event contained useful fields such as:

```text
process.name
process.pid
destination.address
destination.port
network.transport
user.name
```

Some other displayed fields were empty.

### Handling

Only populated fields were used in the final correlation.

Missing values were not reconstructed.

### Lesson

Network telemetry is often richer for some fields than others. Missing process metadata should remain an explicit limitation.

## Issue 5 — Local TCP State Included Unrelated Connections

The following command:

```powershell
Get-NetTCPConnection -State Established |
Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, State, OwningProcess
```

returned multiple active connections.

Examples included Chrome-owned TCP/443 connections.

### Resolution

The `OwningProcess` PID was used to distinguish individual applications.

For example:

```text
PID 24112
    |
    +-- Chrome
```

was validated with:

```powershell
Get-Process -Id 24112
```

### Lesson

An endpoint can have many simultaneous network connections. PID-to-process correlation is essential.

## Issue 6 — `curl.exe` Network Event Was Easier to Find After Process Correlation

The controlled `curl.exe` event was identified through:

```esql
FROM logs-*
| WHERE process.command_line LIKE "*example.com*"
```

This returned one result.

The network event was then located using:

```esql
FROM logs-*
| WHERE destination.address == "172.66.147.243"
```

### Lesson

Known process artifacts and known destination artifacts can be used together to reconstruct the same activity from different telemetry perspectives.

---

## Issue 7 — Time Range

The initial investigation used:

```text
Last 15 minutes
```

This was appropriate because the controlled request was generated immediately before the queries.

If the event is not found:

```text
Last 15 minutes
```

should be expanded temporarily.

### Lesson

Network events are timestamp-sensitive and can quickly become buried under normal background traffic.
