# elastic-security-suspicious-network-connection-endpoint-investigation-lab
## Overview
A network connection becomes useful to a SOC analyst when it is correlated with the endpoint process that created it.

The investigation model is:

Network Connection
      ↓
Source Host
      ↓
Destination
      ↓
Port / Protocol
      ↓
Initiating Process
      ↓
Parent Process
      ↓
User
      ↓
Command Line
      ↓
Related Activity
      ↓
Assessment

For example:

pwsh.exe
    ↓
curl.exe
    ↓
HTTPS connection
    ↓
example.com
    ↓
TCP 443

The important distinction is:

Outbound connection
    ≠
Malicious traffic

and:

Unusual process making an HTTPS connection
    ≠
Confirmed command-and-control

A SOC analyst should investigate:

Which process initiated the connection
Which user was responsible
Where the connection went
Which port and protocol were used
Whether the destination is expected
Whether the process normally communicates over the network
What parent process launched it
What happened before and after the connection

This lab investigates an outbound network connection generated by a Windows endpoint using **Elastic Security and Elastic Defend**.

The investigation focuses on correlating a network connection with the process that initiated it, identifying the destination address and port, examining the process ancestry and user context, and comparing the controlled activity with other network connections already present on the endpoint.

A controlled HTTPS request was generated using `curl.exe`:

```powershell
curl.exe -I https://example.com
```

The resulting endpoint telemetry was then investigated through Elastic ES|QL.

## Lab Objectives

- Establish a baseline of existing outbound network activity on the Windows endpoint before generating the controlled connection.
- Resolve the controlled destination and compare DNS results with the destination observed in endpoint network telemetry.
- Generate a benign outbound HTTPS connection using `curl.exe`.
- Identify the process responsible for creating the network connection.
- Reconstruct the relationship between `pwsh.exe` and `curl.exe` using process IDs and parent-process information.
- Correlate the initiating process with the destination address, destination port, and transport protocol.
- Validate the controlled network connection using both local Windows TCP information and Elastic telemetry.
- Investigate whether the destination observed in Elastic matches the destination resolved for the controlled hostname.
- Compare the controlled `curl.exe` connection with normal HTTPS activity generated by applications such as Chrome and Photos.
- Examine why a broad TCP/443 search can return many legitimate connections and how process context reduces ambiguity.
- Investigate network activity using process name, user context, timestamp, destination, and port rather than relying on the port number alone.
- Document incomplete or unavailable network and process fields without filling the gaps through assumptions.
- Distinguish a suspicious-looking outbound connection from evidence that actually demonstrates malicious communication.
- Practice correlating process execution, DNS resolution, network connection telemetry, and endpoint context into a single investigation timeline.
- Document the controlled activity as benign and identify which forms of malicious network behavior were not demonstrated by the available evidence.

## Lab Scenario

A SOC analyst is investigating an outbound network connection generated by a Windows endpoint. The analyst wants to determine which process initiated the connection, which destination it contacted, and whether the activity is consistent with normal application behavior or requires additional investigation.

A controlled HTTPS request is generated from PowerShell using:

```powershell
curl.exe -I https://example.com
```

Before and after the request, the analyst validates the destination through DNS resolution and reviews established TCP connections on the endpoint.

Elastic telemetry is then used to correlate the activity across multiple evidence sources. The investigation focuses on:

- The initiating process and its parent process
- Process ID and user context
- Command-line arguments
- Destination address and port
- Network transport
- DNS resolution results
- Other applications generating outbound HTTPS traffic
- Differences between controlled activity and existing endpoint connections

The controlled request produces an HTTPS connection to `172.66.147.243` over TCP port `443`. Elastic telemetry links the connection to `curl.exe`, while broader network telemetry shows other applications such as Chrome and Photos.exe also making HTTPS connections.

The investigation therefore emphasizes that an outbound connection, including TCP/443 traffic, is not automatically malicious. The analyst must correlate **process, destination, user, command line, and surrounding activity** before determining whether the connection warrants further investigation.

The activity is intentionally benign. No malicious payload, command-and-control infrastructure, or data-exfiltration activity is introduced. The scenario is designed to demonstrate how endpoint network telemetry can be reconstructed and assessed using evidence from both the host and Elastic.

## Controlled DNS Resolution

The destination was resolved locally with:

```powershell
Resolve-DnsName example.com
```

Observed addresses included:

```text
172.66.147.243
104.20.23.154
```

and an IPv6 address:

```text
2606:4700:9765:72db:f2a5:0:ef6b:ff98
```

The investigation used the actual destination observed in Elastic when correlating the connection.

## Controlled HTTPS Request

The following command was executed:

```powershell
curl.exe -I https://example.com
```

The request returned:

```text
HTTP/1.1 200 OK
```

The response contained normal HTTP headers including:

```text
Content-Type: text/html; charset=utf-8
Connection: keep-alive
Server: cloudflare
```

No payload was downloaded or executed.

## Process Correlation

Elastic recorded the controlled `curl.exe` process:

```text
Timestamp: Sep 30, 2026 @ 04:13:21.732
Host: desktop-9mmm37v
User: Dell
Process: curl.exe
PID: 12968
Parent: pwsh.exe
Parent PID: 34288
Executable: C:\Windows\System32\curl.exe
```

The command line referenced:

```text
https://example.com
```

This established the controlled process relationship:

```text
pwsh.exe
    |
    +-- curl.exe
          |
          +-- HTTPS request
```

## Network Telemetry

Elastic recorded a network event for the controlled request at:

```text
Sep 30, 2026 @ 04:13:21.865
```

Observed:

```text
Host: desktop-9mmm37v
User: Dell
Process: curl.exe
PID: 12968
Destination: 172.66.147.243
Destination Port: 443
Transport: tcp
```

The destination was consistent with the locally resolved `example.com` address observed before the request.

## Destination Investigation

The following query was used:

```esql
FROM logs-*
| WHERE destination.address == "172.66.147.243"
| KEEP @timestamp, host.name, user.name, process.name, process.pid, process.parent.name, destination.address, destination.port, network.transport
| SORT @timestamp DESC
```

Elastic returned one matching document corresponding to the controlled `curl.exe` connection.

## HTTPS Network Baseline

A broader query was performed:

```esql
FROM logs-*
| WHERE event.category == "network"
| WHERE destination.port == 443
| KEEP @timestamp, process.name, process.parent.name, user.name, destination.address, destination.port
| SORT @timestamp DESC
```

This returned multiple HTTPS connections.

Observed applications included:

```text
chrome.exe
Photos.exe
curl.exe
```

Examples included Chrome connections to:

```text
172.64.155.209
104.18.32.47
64.239.123.1
44.219.165.61
```

and a Photos.exe connection to:

```text
13.107.5.93
```

These observations demonstrate that outbound HTTPS traffic is common on the endpoint.

## Endpoint TCP Validation

The local endpoint was checked with:

```powershell
Get-NetTCPConnection -State Established |
Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, State, OwningProcess
```

Existing connections included TCP/443 sessions owned by different processes.

For example, Chrome PID `24112` had established connections to:

```text
76.223.31.44:443
104.18.39.21:443
```

Other processes also had established TCP/443 connections.

This reinforced the need to correlate network activity with the responsible process instead of treating all outbound HTTPS traffic as suspicious.

## Key Findings

### Observed

- `curl.exe` generated a controlled HTTPS request.
- The process ran as user `Dell`.
- `curl.exe` PID was `12968`.
- Its parent was `pwsh.exe` PID `34288`.
- The executable path was `C:\Windows\System32\curl.exe`.
- The controlled destination was `172.66.147.243`.
- The destination port was `443`.
- The transport protocol was TCP.
- `example.com` resolved locally to `172.66.147.243` and `104.20.23.154`.
- Elastic correlated the process and network events.
- Other normal applications were also generating outbound HTTPS traffic.

### Confirmed

- The controlled `curl.exe` process executed successfully.
- The HTTPS request to `example.com` returned `HTTP/1.1 200 OK`.
- Elastic captured both process and network telemetry for the controlled connection.
- The destination address `172.66.147.243` was associated with the controlled network event.
- No malicious payload was downloaded or executed.

### Not Demonstrated

- Command-and-control
- Malware communication
- Data exfiltration
- Persistence
- Credential theft
- Confirmed compromise

## MITRE ATT&CK

This lab is primarily an endpoint network-investigation exercise rather than a demonstration of a specific attack technique.

No command-and-control or exfiltration technique was demonstrated by the controlled activity.

## Telemetry Notes

A broader HTTPS query returned many events because normal applications such as Chrome and Photos.exe were also communicating over TCP/443.

This demonstrated that destination port, process name, and user context should be considered together.

The investigation also showed that process-to-network correlation provides stronger evidence than examining network connections independently.
